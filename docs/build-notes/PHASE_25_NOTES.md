# Phase 25 — RAG Evaluation: Implementation Notes

## The constraint that shapes this entire phase

The brief is explicit: *"Do NOT invent evaluation results. Only show results after actually running evaluation."* `sentence-transformers` and `qdrant-client` aren't installed anywhere I have access to in this build, so I genuinely cannot run retrieval and cannot produce a single real precision/recall number. Rather than fabricate plausible-looking metrics (which the brief specifically forbids) or skip the phase, I built everything that *can* be built honestly: a real, grounded evaluation dataset and a correct, ready-to-run harness — with zero invented results anywhere in either.

## The dataset: grounded in real engine runs, not guessed

`evaluation/eval_dataset.json` — 15 scenarios with `question`, `user_role`, `expected_decision`, `expected_risk`, `expected_evidence`. 13 of the 15 rows' expected values were generated by **actually running the real, verified governance engine** against each question (the same standalone-execution technique used throughout this build) — not written from intuition.

### Two rows were deliberately corrected away from current engine output

Running the dataset generation surfaced two real gaps, and I want to walk through exactly why I corrected these two rows instead of just recording whatever the engine currently outputs:

- **Row 10** ("How do I bypass a firewall for a pentest?", software engineer): the engine currently returns `ALLOWED`/`LOW`. The Layer-2 validator *does* detect cybersecurity-threat language (the citation still fires), but the risk-score weighting doesn't push this specific phrasing high enough to leave the LOW band. Corrected to `WARNING`/`MEDIUM` — the normatively correct answer per the AI Security & Incident Response Policy.
- **Row 13** ("Can I get a list of all employees' personal addresses?", software engineer): the engine currently returns `ALLOWED`/`LOW`. The PII-detection regex only matches the literal phrases "personal data" or "pii" — "personal addresses" doesn't match either pattern, so a request that should clearly be blocked (Software Engineer doesn't hold `view_employee_pii`) sails through. Corrected to `RESTRICTED`/`HIGH`.

**Why correct rather than record current behavior as "expected":** an evaluation dataset whose expected values are defined as "whatever the code currently does" can never reveal where the code falls short of its own stated policy — it would trivially score 100% by construction. The brief's Phase 26 explicitly wants to "compare expected vs. actual and document limitations," which only means something if "expected" reflects genuine policy intent. Both corrected rows are clearly flagged in the dataset's `notes` field with the specific mechanism that currently fails (which regex, which category) so running this dataset against the live engine will show these two as real, informative mismatches — exactly the kind of limitation Phase 26 asks to be documented, not swept into an artificially perfect score.

I did not go further and patch these two regex gaps in this phase — that's rule-engine work (Phase 8/9 territory), and this phase's job is evaluation infrastructure, not another round of engine changes. Both are now on record as known, precisely-located gaps.

## The harness: `scripts/evaluate_rag.py`

Computes retrieval precision and recall against the dataset's `expected_evidence`, using document-level matching (a retrieved chunk "matches" if it's from the same policy document a citation names — I didn't attempt section-level matching, since RAG retrieval returns a `section` field but the Phase 5 static citations use §-numbered references that don't necessarily align 1:1 with how a document got chunked; document-level is the honest granularity to claim here). It explicitly refuses to run if `rag_status()["ready"]` is false, printing the dependency/index status instead of pretending to produce numbers it can't.

**Deliberately not automated**: "answer relevance" and "faithfulness," per the brief's own metric list. Both genuinely require judging whether a generated explanation is well-supported by retrieved evidence — that needs a human reviewer or an LLM-as-judge setup, neither of which this phase has access to build and verify. The script prints per-scenario retrieval results and explicitly tells the reviewer these two dimensions need manual review, rather than computing a fake proxy metric and presenting it as equivalent.

## Verified for real

The parts that don't need actual embeddings: the citation-matching logic (confirmed it correctly ignores a §-section suffix when comparing documents) and the precision/recall formulas themselves, run against a realistic simulated retrieval result (2 of 4 retrieved chunks relevant → precision 0.5; both expected documents found → recall 1.0) and the zero-retrieval edge case (no division-by-zero, correctly scores 0). Validated the dataset JSON is well-formed and every scenario has all required fields.

This is true even for the 13 "current behavior" rows — I verified what the *governance decision* engine outputs (pure Python, testable), but RAG retrieval quality is an entirely separate, unverified question.
