# Phase 21 — Security Hardening: Implementation Notes

This phase is explicitly a checklist review against the brief's Phase 21 list. Rather than treat it as "build new features," I went through each item and either confirmed it was already handled (citing where), fixed a real gap, or explicitly scoped out something not worth doing given the constraints of this environment — the same discipline as every other phase.

## Fixed this phase

**JWT tokens never expired at all** (`JWT_ACCESS_TOKEN_EXPIRES = False`) — flagged in the very first Phase 0 audit and never actually fixed until now. Set to a configurable expiry (`JWT_ACCESS_TOKEN_EXPIRES_HOURS`, default 8 hours). This required a companion frontend fix: added a global axios response interceptor (`api.js`) that clears the token and redirects to `/login` on any 401 — **except** the login endpoint itself, so a wrong-password attempt shows a form error rather than triggering a redirect loop. Verified this exact branching logic with 4 real test cases (wrong password on login, expired token mid-session, already-on-login-page guard, non-401 errors like a 403 permission denial).

**Wildcard CORS + an invalid credentials combination.** `origins: "*"` paired with `supports_credentials=True` is actually rejected by browsers (the CORS spec forbids wildcard origin with credentials) — and `supports_credentials` was never needed anyway, since this app authenticates via a JWT in the `Authorization` header, not cookies. Replaced with a configurable origin allowlist (`CORS_ORIGINS` env var, defaulting to the Vite dev server) and dropped `supports_credentials` entirely.

**`DEBUG` defaulted to ON.** Combined with `host="0.0.0.0"` (all network interfaces, not just localhost), a fresh checkout run with zero configuration exposed Flask's interactive debugger and full stack traces to anything that could reach the machine on the network. Flipped the default to off — opt-in via `DEBUG=1`, not opt-out.

**Default secrets were silent.** `SECRET_KEY`/`JWT_SECRET_KEY` still fall back to working dev defaults (so a zero-config demo run still works), but now print a loud startup warning if either default is still in use, rather than silently shipping an insecure configuration nobody notices.

**No global JSON error handling.** An unhandled exception or an unmatched route previously fell through to Flask's default HTML error page — wrong shape for a JSON API, and 500s weren't explicitly logged server-side. Added `@app.errorhandler` for 404, 500, and a catch-all `Exception` handler that returns a generic message to the client (never a stack trace) while logging the real exception via `app.logger.exception()`.

**No request size limit at all.** Set `MAX_CONTENT_LENGTH` to 8MB — comfortably covers a face-image upload with room to spare, while bounding worst-case memory usage from an oversized or malicious request body. This also incidentally routes 413 (Request Entity Too Large) through the same JSON error handler via its `HTTPException` branch.

**No message length cap on `/chat`**, independent of the new whole-request size cap — added a 4000-character limit so a single oversized message can't blow up the in-memory `_histories` conversation buffer or blow past an AI provider's context window.

**Login had no rate limiting.** Added a small, dependency-free in-memory limiter (`app/services/rate_limit.py`) — 5 attempts per 60 seconds, keyed by **(IP, username)** rather than username alone, so an attacker can't lock a real user out of their own account by deliberately failing logins against them from an unrelated IP. Resets on a successful login. **Ran 4 real executable tests** (this module has zero Flask/DB dependency): 5 attempts allowed through, the 6th correctly blocked, a different IP targeting the same username is unaffected by the first attacker's lockout, and username matching is case-insensitive (so "Bob" and "bob" share one counter rather than offering a trivial bypass).

**Created `.env.example`** — generated by grepping every actual `os.getenv()` call across the backend, not written from memory, so every documented variable genuinely does something.

## Already handled in earlier phases (confirmed, not re-done)

- Password hashing: `werkzeug.security`, confirmed real since Phase 0
- SQL injection: SQLAlchemy ORM throughout; no raw string-interpolated queries anywhere I've found across 21 phases of reading this codebase
- Role/permission checks: `require_role`/`require_permission` decorators (Phase 2), used throughout Phases 9–20
- Protected admin routes: audited and fixed specifically in Phases 19 (Ghost Mode) and 20 (Attack Simulation)
- Audit logging: comprehensive as of Phase 12
- No secrets in frontend: grepped for common API key patterns (`sk-...`, `AIza...`, generic `api_key: "..."`) across the entire frontend source — none found

## Explicitly scoped out, not silently skipped

- **The rate limiter is single-process, in-memory, and resets on restart.** Documented in the module's own docstring as adequate for this capstone's single-process deployment, explicitly not production-grade for multiple worker processes (which would each keep separate counts) — a real deployment should use Flask-Limiter with a shared backend like Redis instead. I didn't add that dependency because it's another untestable new package in this sandbox, and the brief says "rate limiting where appropriate" — appropriate here meant something that actually works with zero new dependencies, not the most robust possible implementation.
- **Secure PDF processing**: `pypdf`/LangChain's `PyPDFLoader` are established libraries handling untrusted PDF parsing; I did not add extra sandboxing beyond what they provide, since building custom PDF-parsing hardening is out of scope for a capstone and neither library has a specific known vulnerability I'm working around here.

## What I could NOT verify

Whether the app actually starts cleanly with all these config changes together, whether a real browser session correctly gets redirected on an expired token (vs. some edge case in how axios surfaces the 401), and whether the rate limiter's IP extraction (`X-Forwarded-For` header, falling back to `request.remote_addr`) behaves correctly behind a real reverse proxy vs. direct connection. The rate limiter's *decision logic* is genuinely tested; its *integration* into the live login flow is not.
